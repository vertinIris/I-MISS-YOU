# 飞行雪绒 · Snow — 技术选型分析报告

> **版本**：v1.0 · 2026-08-11
> **项目**：飞行雪绒 · Snow（I-MISS-YOU）
> **分析范围**：Web Application vs 移动原生 / 桌面 / 混合 / PWA
> **决策结论**：**维持 Web Application（当前方案）**，附 PWA 渐进增强

---

## 一、执行摘要

本报告对飞行雪绒·Snow 项目的五种技术路径进行系统评估。基于项目核心约束——**非商业同人项目、零预算、个人维护、目标用户为《鸣潮》玩家社区、强依赖实时社区互动与多媒体内容展示**——得出以下结论：

| 排序 | 方案 | 综合评分 | 推荐度 |
|---|---|---|---|
| **1** | **Web Application**（当前） | **9.2 / 10** | ✅ **强烈推荐** |
| 2 | PWA（渐进增强） | 8.1 / 10 | ✅ 推荐叠加 |
| 3 | 混合应用（Flutter/RN） | 4.5 / 10 | ❌ 不推荐 |
| 4 | 桌面应用（Electron/Tauri） | 3.2 / 10 | ❌ 不推荐 |
| 5 | 移动原生（iOS/Android） | 2.1 / 10 | ❌ 强烈不推荐 |

**核心论点**：项目的所有功能需求（内容展示、社区互动、实时同步、多媒体）均可在 Web 平台完整实现，且 Web 在**可达性、开发成本、维护效率、更新分发**四个维度具有不可替代的优势。其他方案要么成本超出个人项目承受范围，要么无法提供超过 Web 的增量价值。

## 三、方案概述

### 方案 A：Web Application（当前）

**架构**：HTML5 + CSS3 + 原生 JS + Supabase（PostgreSQL + Auth + Realtime + Storage + RLS）

```
浏览器 → GitHub Pages / CloudBase CDN
           ↓
         静态 HTML/CSS/JS（含 Terser 压缩 bundle）
           ↓
         Supabase Cloud（Auth + DB + Realtime + Storage）
```

**技术特性**：
- 零框架，原生 JS + IIFE 模块
- Supabase 提供完整 BaaS（Auth/DB/Realtime/Storage/RLS）
- CDN 分发，TTFB < 200ms（CloudBase）
- 阶段 II 已完成：JS 合并（18→1 bundle）+ CSS 压缩 + SRI + Source Map

### 方案 B：PWA（渐进增强）

**架构**：在现有 Web 基础上叠加 Service Worker + Web App Manifest + Push API

```
浏览器 → Web App（同方案 A）
  ↓ 叠加
Service Worker（离线缓存 + 后台同步）
Web App Manifest（可安装到桌面/主屏幕）
Push API（推送通知）
```

**技术特性**：
- 不改变现有架构，仅增量添加
- 支持离线访问缓存内容
- 可安装到手机主屏幕（类似原生 App）
- 需 HTTPS（已有）

### 方案 C：混合应用（Flutter / React Native）

**架构**：跨平台框架 + WebView 或原生渲染 + Supabase SDK

```
Flutter/RN 应用
  ↓ Dart/JSX → 原生渲染
Supabase SDK（Dart/JS 版本）
  ↓
iOS App Store + Google Play
```

**技术特性**：
- 一套代码 → iOS + Android
- 原生渲染（性能接近原生）
- 需要重新实现所有 UI 组件
- 需要应用商店审核

### 方案 D：桌面应用（Electron / Tauri）

**架构**：Web 前端 + 原生壳 + Node.js/Rust 后端

```
Electron/Tauri 应用
  ↓ Chromium WebView（Electron）或 WRY（Tauri）
Web 前端（可复用现有 HTML/CSS/JS）
  ↓
Windows + macOS + Linux
```

**技术特性**：
- 可复用现有 Web 前端
- 可访问本地文件系统
- Electron 包体积大（~80MB+）；Tauri 轻量（~3MB）
- 需要各平台构建和分发

### 方案 E：移动原生（iOS Swift + Android Kotlin）

**架构**：双平台独立原生开发

```
iOS App（Swift + UIKit/SwiftUI）  +  Android App（Kotlin + Jetpack Compose）
           ↓                                    ↓
     App Store                         Google Play
           ↓                                    ↓
     Supabase Swift SDK               Supabase Kotlin SDK
```

**技术特性**：
- 最佳性能和原生体验
- 完整设备能力访问
- 两套独立代码库
- 最高开发成本

### 4.4 目标用户体验分析

**目标用户画像**：《鸣潮》玩家，年龄 16-30，手机为主（70%）+ PC 为辅（30%），技术素养中等，习惯社交媒体和即时反馈。

| 体验维度 | Web App | 混合/原生 | 差距 |
|---|---|---|---|
| 首次访问门槛 | ✅ 点击链接即看 | ❌ 需下载安装 | **Web 胜出**（降低 80% 流失） |
| 分享传播 | ✅ URL 直接分享 | ❌ 需应用商店搜索 | **Web 胜出** |
| 更新体验 | ✅ 自动最新版 | ❌ 需手动更新 | **Web 胜出** |
| 操作流畅度 | ⚠️ 良好 | ✅ 最佳 | 原生略胜（但本项目交互不重） |
| 推送通知 | ❌ 无 | ✅ 有 | 原生胜（但非核心需求） |
| 离线使用 | ❌ 无 | ✅ 有 | 原生胜（但本项目需在线交互） |

**关键判断**：对于同人社区项目，**首次访问门槛和分享传播**的权重远高于操作流畅度。玩家从社交媒体点击链接 → 立即看到内容 → 参与评论，这个转化漏斗在 Web 上最优。

## 五、建议方案论证

### 5.1 推荐方案：Web Application + PWA 渐进增强

```
┌─────────────────────────────────────────────────────────┐
│                    推荐架构                              │
│                                                         │
│  基础层（已完成）                                        │
│  ├── HTML5 + CSS3 + 原生 JS（零框架）                   │
│  ├── Supabase（Auth + DB + Realtime + Storage + RLS）   │
│  ├── Terser bundle + CSS 压缩 + SRI                    │
│  └── GitHub Pages + CloudBase CDN 双部署               │
│                                                         │
│  增强层（建议追加，3-5 天）                              │
│  ├── PWA Service Worker（离线缓存静态资源）             │
│  ├── Web App Manifest（可安装到主屏幕）                  │
│  ├── Push API（新评论/投稿推送，可选）                   │
│  └── Background Sync（弱网评论排队，可选）              │
│                                                         │
│  不做                                                    │
│  ├── 原生/混合应用（成本不匹配）                        │
│  ├── 桌面应用（用户场景不匹配）                          │
│  └── 框架迁移（无收益，高风险）                          │
└─────────────────────────────────────────────────────────┘
```

### 5.2 论证过程

#### 论点 1：成本-收益比最优

```
Web App（当前）      成本 ¥0      收益 100% 功能    → 成本收益比 ∞
PWA 叠加            成本 3-5 天   收益 +离线+推送   → 成本收益比 高
混合应用            成本 60-90 天 收益 +原生手感    → 成本收益比 低（手感非核心需求）
移动原生            成本 120-180天 收益 +最佳性能   → 成本收益比 极低（个人项目不可承受）
```

#### 论点 2：用户转化漏斗最优

```
社交媒体分享链接 → 用户点击
  │
  ├─ Web App：    点击 → 1.5s 看到内容 → 参与评论        转化率 ~60%
  ├─ PWA：        点击 → 1.5s 看到内容 → 提示安装        转化率 ~60% + 留存↑
  ├─ 混合/原生：  点击 → 跳转应用商店 → 下载 → 安装 → 打开  转化率 ~5-10%
```

> 同人内容的传播路径是「即时兴趣 → 即时消费」，任何安装门槛都会导致 80-90% 的用户流失。

#### 论点 3：维护可持续性

```
Web App 维护：
  · 代码变更 → git push → CDN 自动更新 → 全用户立即生效
  · 单人可维护，每次更新 5-10 分钟
  · 无版本碎片（只有一份最新版）

原生应用维护：
  · 代码变更 → 构建 → 测试 → 提交审核 → 上架 → 用户手动更新
  · 单人难以维护双平台
  · 版本碎片（不同用户运行不同版本，需兼容处理）
  · 每次 Supabase SDK 升级需同步更新两端
```

#### 论点 4：已有技术资产保护

当前项目已有：
- 18 个主站 JS 模块 + 15 个论坛 JS 模块（阶段 II 已合并压缩）
- 12 个 CSS 文件（已压缩为 3 个 min.css）
- 31 个 SQL migration（完整的数据库 Schema + RLS + RPC）
- Supabase 完整后端（Auth + Realtime + Storage + Rate Limiter）
- CI/CD 管道（GitHub Actions + smoke-check + extreme-audit）

**这些资产在 Web App 方案下 100% 复用。** 转向其他方案意味着：
- 混合/原生：UI 全部重写（0% 复用），后端逻辑可部分复用（Supabase SDK）
- 桌面：前端 70% 可复用，但需适配原生壳
- **沉没成本**：放弃现有资产 = 浪费 6+ 个月的开发投入

#### 论点 5：PWA 填补 Web 的主要短板

Web App 的三个主要短板（离线、推送、安装感）均可通过 PWA 解决：

| 短板 | PWA 解决方案 | 实现成本 |
|---|---|---|
| 无离线能力 | Service Worker 缓存静态资源 | 2 天 |
| 无推送通知 | Web Push API + Supabase Webhook | 2 天 |
| 无安装感 | Web App Manifest + Add to Home Screen | 0.5 天 |

PWA 是**纯增量**，不改变现有架构，不破坏现有功能，可随时回退。

## 六、风险评估与缓解措施

### 6.1 推荐方案（Web + PWA）的风险

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| W1 | **Supabase 免费档耗尽**（500MB DB / 50k MAU） | 🟡 中 | 🔴 高 | 监控用量；超出后升级 Pro（$25/月）或迁移自建 |
| W2 | **CloudBase 免费流量耗尽**（5GB/月） | 🟢 低 | 🟡 中 | 监控流量；超出后升级或回退 GitHub Pages |
| W3 | **浏览器兼容性**（旧版 Safari/IE） | 🟢 低 | 🟡 中 | 已用 `typeof` 守卫；CSP 已配置；不做 IE 支持 |
| W4 | **PWA Service Worker 缓存过期** | 🟡 中 | 🟡 中 | SW 版本管理 + `skipWaiting` + `clients.claim` |
| W5 | **Supabase Realtime 断连** | 🟡 中 | 🟡 中 | 已有断线重连（SyncManager）；PWA Background Sync 补充 |
| W6 | **CSP 限制第三方集成** | 🟢 低 | 🟡 中 | CSP 已允许必要域名；新集成需更新 CSP |

### 6.2 不推荐方案的风险（若错误选择）

| # | 风险方案 | 风险 | 后果 |
|---|---|---|---|
| N1 | **移动原生** | 开发周期 6-9 个月 | 项目停滞，用户流失，作者倦怠 |
| N2 | **混合应用** | 应用商店审核被拒（同人内容） | 投入沉没，无法上架 |
| N3 | **桌面应用** | 用户场景不匹配 | 无人下载，维护浪费 |
| N4 | **框架迁移**（React/Vue 重写） | 高风险重构，无增量价值 | 6+ 月重写，引入新 bug，失去现有稳定性 |
| N5 | **任何需要应用商店的方案** | 同人内容审核风险 | Apple/Google 可能因 IP 问题下架 |

### 6.3 风险应对策略

```
策略 1：双部署并行（已实施）
  GitHub Pages（全球，永久备用） + CloudBase（大陆 CDN）
  → 任一平台故障，另一个仍可用

策略 2：渐进增强（建议实施）
  基础功能不依赖 PWA/Service Worker
  → PWA 失败不影响核心功能

策略 3：后端可迁移性
  Supabase 用标准 PostgreSQL + 标准 SQL
  → 必要时可迁移到自建 PostgreSQL + Express

策略 4：代码无框架锁定
  原生 JS + IIFE，无 React/Vue 依赖
  → 未来如需迁移框架，前端代码可逐模块替换
```

## 七、结论

### 7.1 最终建议


### 7.2 PWA 实施优先级（如决定追加）

| 优先级 | 功能 | 工作量 | 价值 |
|---|---|---|---|
| P1 | Web App Manifest（可安装） | 0.5 天 | 用户可添加到主屏幕，提升留存 |
| P2 | Service Worker（静态缓存） | 2 天 | 二次访问 0.3s 加载，弱网可用 |
| P3 | Push API（评论推送） | 2 天 | 用户离线时收到新评论通知 |
| P4 | Background Sync（评论排队） | 1 天 | 弱网下评论不丢失 |

### 7.3 决策检查清单

在做出最终决策前，请确认以下问题：

- [ ] 项目是否需要离线使用核心功能？（否 → Web 足够）
- [ ] 目标用户是否愿意下载安装 App？（否 → Web 最优）
- [ ] 是否有预算支持应用商店年费和开发成本？（否 → Web 唯一选择）
- [ ] 是否有团队支持双平台原生开发？（否 → Web 唯一选择）
- [ ] 项目是否需要 App Store/Google Play 的分发渠道？（否 → Web + SEO 更优）
- [ ] 是否需要设备原生能力（如 NFC、蓝牙、传感器）？（否 → Web 足够）

**如果以上问题中有 5 个以上回答「否」，则 Web Application 是唯一合理选择。**
